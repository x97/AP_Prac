# 全栈项目架构与目录设计

> 目标：在现有“数据生产”基础上，增加 Web、微信小程序和后端 API，并保证内容数据、用户数据、静态资源三条线互不污染。  
> 已确定选型：**FastAPI + 单机 SQLite release + Next.js + 原生微信小程序**；先跑通最小闭环，再迁 PostgreSQL。  
> 当前阶段：**只创建目录骨架，不写前后端代码**。现有数据管道仍在根目录，迁移放到最后。

---

## 1. 先分层，不要先堆目录

系统实际有四条独立链路：

```text
数据生产（离线）
  data-pipeline → 内容库（只读）→ 内容发布版本

内容服务（在线）
  API → 内容库（只读）+ 用户库（读写）

客户端
  Web / 微信小程序 → API

静态资源
  源文件 assets/ → 对象存储/CDN → Web / 小程序
```

关键原则：

1. **内容库与用户库分离**：题库/知识点是只读内容；用户、答题记录、进度是读写数据。
2. **只有 API 能访问数据库**：Web 和小程序不能直连数据库，也不能读本地文件路径。
3. **内容发布有版本**：数据管道产出 `content release`，API 指定版本；可回滚。
4. **静态资源走 CDN**：小程序主包不能塞大量图片；API 返回 URL，不返回本地路径。
5. **数据管道不进入请求链路**：解析/抽取/重算权重是离线任务，不在 API 请求里跑。
6. **契约先行**：API schema 是 Web/小程序/后端共同契约。

## 4. 数据层：内容库 vs 用户库

### 内容库（只读）

- 科目源库：`data/content/<subject>/<subject>_exam.db` + `<subject>_knowledge.db`
- papers / questions / options / concepts / relations
- 由 data-pipeline 离线生成；发布时合并所有 enabled 科目
- API 只读，带缓存
- 发布版本：`content_release_id`

### 用户库（读写）

建议 PostgreSQL，最小表：

```text
users
user_identities        # wechat openid / unionid（邮箱密码在主表 users）
sessions
attempts               # 一次答题
attempt_answers        # 每题作答
bookmarks
study_progress
wrong_questions
events                 # 可选：埋点
```

内容库和用户库可以同实例不同 schema，也可以分开实例。不要混在题库表里。

### 内容发布

```text
data/releases/content-YYYYMMDD-01/
  exam.db                # 所有 enabled 科目合并
  knowledge.db
  assets/<subject>/...   # 各科目资产
  assets-manifest.json   # asset_id -> CDN key/hash
  release.json           # release_id / subjects / counts / checksum
  exclusions.json
```

API 启动或发布时读取 `content_release_id`；需要回滚就切回旧 release。

## 5. API 设计

### 路由

```text
GET  /api/v1/content/version
GET  /api/v1/papers?subject=psychology
GET  /api/v1/papers/{paper_id}
GET  /api/v1/papers/{paper_id}/questions
GET  /api/v1/practice-groups
GET  /api/v1/concepts?unit=1
GET  /api/v1/concepts/{concept_id}
POST /api/v1/attempts
PATCH /api/v1/attempts/{attempt_id}
GET  /api/v1/me/progress
POST /api/v1/auth/wechat
POST /api/v1/auth/web
```

### 单元练习统一模型

学生端不选择题库：

```text
GET /api/v1/practice-groups?subject=psychology
→ [
    {
      "group_id": "psychology-unit1-practice",
      "unit_id": "1",
      "title": "Unit 1 单元练习",
      "paper_id": "psychology-unit1-practice-bundle",
      "question_count": 345
    }
  ]
```

- `paper_id` 是 `practice_bundle` 虚拟卷。
- 成员映射由 `config/practice_groups/<subject_id>.json` 管理；官方题库必须是 `primary`，教材章节是 `supplement`。
- CB 题在前，Barron 题作为 supplement 追加。
- `practice_groups.bundle_paper_id` 保存这个映射。
- 来源 `CB / Barron` 只保留在数据层/后台，不在学生端做题库选择。
- 新单元规则：CB 必须是 `primary`，Barron 只做 `supplement`；没有 CB 的单元标 `needs_review`，不静默把 Barron 升为 primary。

### 响应规则

- 内容对象返回 `asset_url`（本地为带 `exp`/`sig` 的签名 URL），不返回 `assets/psychology/...` 本地路径。
- 列表分页用 cursor，不用 offset 大页码。
- 内容响应加 `content_release_id` 和 `ETag`。
- 用户写操作必须鉴权；内容读可匿名。
- 错误统一 `{code, message, request_id}`。

### 契约

- `packages/api-contracts/openapi.yaml`
- FastAPI 生成 OpenAPI 快照，CI 比对
- 生成 TypeScript client 给 Web / 小程序
- 不在 Web/小程序手写重复类型

## 7. 微信小程序

原生小程序优先；如果团队想复用 React，可用 Taro，但先按原生设计：

```text
apps/miniprogram/
  pages/
    home/
    unit/
    quiz/
    result/
    knowledge/
    profile/
  components/
  services/api.ts
  utils/auth.ts
  app.json
  project.config.json
```

关键约束：

- 主包 2MB、总包 20MB；题目图片必须 CDN，不打进包。
- 请求域名必须 HTTPS 且加入小程序后台白名单；国内服务器通常需要备案。
- `wx.login` 的 code 发后端换 session；**AppSecret 只能在后端**。
- 答题/进度写用户库，不写内容库。
- 大模块用分包（quiz/knowledge）。
- 小程序不读 `assets/` 本地路径。

## 10. 数据更新后如何同步到后端

这是当前数据端和在线端之间最关键的一条链路。**不要让 API 直接读你本地刚改完的 SQLite 文件**；应该走“内容发布（content release）”。

### 10.1 推荐流程

```text
数据管道更新本地内容库
→ 跑 QA（计数/路径/概念/权重/integrity）
→ 生成 release 产物
→ 上传 release 到对象存储/服务器
→ 上传/同步 assets 到 CDN
→ 调后端内部接口激活 release
→ 后端切 active_release
→ smoke test
→ 旧 release 保留，可回滚
```

### 10.2 Release 目录

```text
data/releases/content-YYYYMMDD-01/
  release.json          # release_id / subjects / counts / checksums
  exam.db               # 所有 enabled 科目合并
  knowledge.db          # 所有 enabled 科目合并
  assets/<subject>/...
  assets-manifest.json  # assets.path -> cdn_key / sha256 / size
```

`release.json` 至少包含：

```json
{
  "release_id": "content-20261030-01",
  "subjects": ["psychology"],
  "schema_version": 1,
  "counts": {"papers": 36, "questions": 2876, "concepts": 1105},
  "counts_by_subject": {
    "psychology": {"papers": 36, "questions": 2876, "concepts": 1105}
  },
  "checksums": {"exam.db": "sha256:...", "knowledge.db": "sha256:..."},
  "created_at": "2026-10-30T09:00:00+08:00"
}
```

### 10.3 后端激活接口

只对内网/服务令牌开放，不暴露给学生端：

```text
POST /internal/content/releases
Authorization: Bearer <pipeline-service-token>
{
  "release_id": "...",
  "exam_url": "s3://.../exam.db",
  "knowledge_url": "s3://.../knowledge.db",
  "checksums": {"exam.db": "sha256:...", "knowledge.db": "sha256:..."},
  "assets_manifest_url": "s3://.../assets-manifest.json"
}
```

后端行为：

1. 下载到 staging。
2. 校验 checksum / counts / schema_version。
3. 导入 `content_staging`（Postgres）或校验 SQLite 文件。
4. 事务内切换 `active_release_id`。
5. 清缓存。
6. 返回 active version。
7. 旧 release 保留，回滚只切指针。

### 10.4 两种落地方式

**A. 单机 / 小规模（最快）**

- release 包含新的 `exam.db` + `knowledge.db` 两个文件。
- 后端以只读方式打开 `data/releases/<id>/exam.db` 与 `knowledge.db`。
- `active_release` 存文件路径/版本；切换用指针。
- 适合先跑通 Web MVP；缺点是多实例、并发写、回滚管理较弱。

**B. PostgreSQL（推荐生产）**

- 内容库与用户库分开 schema/实例。
- pipeline 导出 SQL/JSONL，后端导入 `content_staging`。
- `content_release` 表记录版本；业务表带 `release_id` 或使用独立 schema。
- 原子切换 active release。
- 适合 Web + 小程序 + 多实例。

### 10.5 静态资源同步

- `assets/psychology/` 是源文件，不是线上 URL。
- 发布时按 manifest 上传到对象存储：
  - `s3://ap-psych-assets/psychology/images/...`
  - CDN 域名：`https://cdn.example.com/psychology/...`
- 内容库仍可保留 `assets.path` 作为 source key；API 返回：

```json
{
  "asset_id": "...",
  "url": "https://cdn.example.com/psychology/images/2025/fig_q016.png",
  "width": 1100,
  "height": 620
}
```

不要把 `assets/psychology/...` 本地路径直接返回给 Web/小程序。

### 10.6 发布门禁

- 所有 DB 路径存在（当前 0 缺失）
- `integrity_check=ok` / `foreign_key_check=OK`
- 题目/选项/答案计数与 release.json 一致
- 概念/关系/权重计数一致
- assets manifest 覆盖所有被引用 asset
- API smoke test：papers / questions / concepts / practice-groups 各 1 条
- 失败不切换 active release

### 10.7 最小可行版本

先不做 Postgres，也可以：

```text
pipeline 生成 data/releases/<id>/exam.db + knowledge.db
→ scp/rsync 到服务器 releases/
→ 后端 internal API 校验并切 active_release 指针
→ API 重新打开 exam.db + knowledge.db
→ 页面请求带 content_release_id
```

等 Web/小程序流量起来，再迁 Postgres。

## 11. 需要先定的 4 个决策

1. **后端语言**：FastAPI（推荐，复用 Python 数据管线）还是 NestJS（团队全 TS）。
2. **数据库**：生产是否直接上 PostgreSQL；SQLite 只做本地/单机。
3. **小程序框架**：原生（推荐稳定）还是 Taro/uni-app（可复用 React）。
4. **内容发布方式**：SQLite 文件发布，还是 Postgres schema + migration。

这 4 个定了，目录就可以从“推荐骨架”进入实际搭建。
