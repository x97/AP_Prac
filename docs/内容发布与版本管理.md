# 内容发布与版本管理

> 状态：设计定稿（2026-10-29）  
> 适用范围：AP Psychology 当前内容，以及后续多学科内容  
> 相关代码：`_tools/build_merged_release.py`、`_tools/validate_content_release.py`、`apps/api/app/content/store.py`、`apps/api/app/api/v1/admin.py`
>
> **2026-10-30 更新**：多科目内容采用“科目独立源库 → 发布时合并为一个 exam.db/knowledge.db”的方案。  
> 新的源目录、命名、合并构建和迁移以 [`多科目内容源与合并发布.md`](多科目内容源与合并发布.md) 为准。

## 0. 一句话原则

**本地负责生产内容，服务器负责消费内容版本；一个环境只能有一个可写内容源。**

不要把本地 SQLite 和生产 SQLite 当成两个可以同时编辑的数据库。

```text
本地内容源 / Claude Code 数据管道
        │
        │ 构建完整 release
        ▼
不可变 Release
        │
        │ 上传 / 导入
        ▼
服务器 Release 仓库
        │
        │ 激活
        ▼
学生端 API 使用当前 active release
```

---

## 1. 术语

| 术语 | 含义 |
|---|---|
| 内容源 | 可编辑的科目源库 `data/content/<subject>/<subject>_exam.db` / `<subject>_knowledge.db` |
| Release | 从内容源构建出的完整、不可变内容快照 |
| Active Release | 当前学生端实际读取的 Release |
| Staging | 上传后、激活前的临时目录 |
| Import | 上传 Release 包并校验，放入服务器 Release 仓库 |
| Activate | 将某个 Release 切换为 active |
| Archive | 将非 active Release 移入归档区，可恢复 |
| Release Diff | 新旧 Release 的增删改报告 |
| Content Release ID | Release 的唯一标识，例如 `content-20261030-01` |

---

## 2. 核心原则

### 2.1 一个可写内容源

任何时刻只能有一个环境可以写内容：

- Phase 1：本地内容源是唯一可写源
- Phase 2（可选）：服务器内容工作区是唯一可写源

不允许：

```text
本地 DB ⇄ 生产 DB 双向同步
```

否则一定出现覆盖、冲突和无法审计的修改。

### 2.2 Release 不可变

Release 一旦生成，不再修改。

- 修正内容 = 生成新 Release
- 删除内容 = 生成不包含该内容的新 Release
- 回滚 = 切换到旧 Release
- 归档 = 移动 Release，不修改内容

### 2.3 上传和激活分离

```text
上传/导入 ≠ 上线
激活 = 上线
```

上传完成但未激活的 Release 对学生不可见。

### 2.4 全量快照，不做增量 SQL 同步

服务器不执行：

```text
INSERT / UPDATE / DELETE
```

服务器只接收完整 Release，然后切换 active。

新增、删除、修改题目都通过“新 Release 与旧 Release 的差异”表达。

### 2.5 稳定 ID

`question_id`、`concept_id`、`book_id` 等身份 ID 一旦发布，不因为内容修改而重新生成。

内容变化通过 Release 表达；身份变化才产生新 ID。

### 2.6 多科目从第一天就按多科目设计

即使当前只有 AP Psychology，目录、API、active 指针和 Admin 都必须带 `subject_id`。

### 2.7 内容数据与用户数据分离

这是本项目最重要的存储边界：

| 数据 | 存储 | 写入方 | 版本 |
|---|---|---|---|
| 试卷、题目、选项、答案、解析 | Release SQLite `exam.db` | 本地内容管道 | Release 快照 |
| 知识点、概念、教材原文 | Release SQLite `knowledge.db` | 本地内容管道 | Release 快照 |
| FRQ rubric、题目—概念关联 | Release SQLite | 本地内容管道 | Release 快照 |
| 考试配置、练习 topic、exclusions | Release SQLite | 本地内容管道 | Release 快照 |
| 图片、PDF 等文件 | Release `assets/` 或对象存储 | 本地内容管道 | Release 快照 |
| 用户、登录会话 | PostgreSQL / 本地 App SQLite | API | 实时 |
| 练习记录、考试 attempt、答案 | PostgreSQL | API | 实时 |
| 错题、收藏、笔记、题目报错 | PostgreSQL | API | 实时 |
| 用户做题统计、每日统计 | PostgreSQL | API | 实时 |
| 官方卡片复习进度、自定义卡片 | PostgreSQL | API | 实时 |
| 管理员、审计、Release 注册表 | PostgreSQL | Admin API | 实时 |

规则：

```text
内容 Release SQLite = 只读快照
用户数据 PostgreSQL = 可写业务数据
```

不要做：

```text
SQLite questions JOIN PostgreSQL users
```

正确方式：

```text
PostgreSQL 读取用户数据
+
ContentStore 读取 active Release
        │
        ▼
Python 层合并后返回
```

用户数据中保存：

```text
content_release_id
```

重点表：

- `attempts`
- `practice_sessions`

这样旧考试可以按当时的内容版本复盘，而不是强制读取当前 Release。

本地开发可以使用 SQLite 作为 App DB；生产使用 PostgreSQL。  
两种环境都保持同一条边界：内容 Release 与用户数据分开。

## 3. 两种运行模式

### Phase 1：本地权威源（当前推荐）

```text
本地 Claude Code / prompts
  PDF、教材、题目解析、AI 解析、题目—概念关联
        │
        ▼
本地科目源库 data/content/<subject>/<subject>_exam.db / <subject>_knowledge.db
        │
        ▼
构建 Release + Diff
        │
        │ 上传
        ▼
服务器 Release 仓库
        │
        ▼
Admin 导入校验 → 激活
```

职责：

| 环境 | 职责 |
|---|---|
| 本地 | PDF 解析、AI 解析、知识点关联、内容编辑、QA、构建 Release |
| 服务器 Admin | 导入、校验、Diff 查看、激活、回滚、归档、学生数据 |
| 服务器 API | 只读 active Release |
| 服务器生产内容库 | 不作为可编辑源 |

Phase 1 中，生产 Admin **不提供内容编辑**，或者只提供只读查看。  
当前 Admin 的题目/知识点编辑功能只适合本地开发环境。

### Phase 2：服务器内容工作区（后续可选）

如果未来需要：

- 在 Admin 中编辑内容
- 在 Admin 中补 AI 解析
- 在 Admin 中关联知识点
- 多人内容协作

则需要把权威源迁到服务器：

```text
本地解析 → 上传 staging/source 包
        → 服务器内容工作区（唯一可写源）
        → Admin 编辑 / AI worker / 人工审核
        → 构建 Release
        → 激活
```

Phase 2 需要额外解决：

- 服务器工作区数据库
- 本地导入与服务器编辑的合并
- 内容修订历史
- AI job worker
- 审核与权限

**不要同时启用 Phase 1 和 Phase 2 的两套编辑。** 先选一个。

## 4. 目录结构

### 4.1 当前结构（合并 Release）

```text
data/releases/
  content-20261030-01/
    exam.db
    knowledge.db
    assets/
      psychology/...
      statistics/...        # 启用后
    assets-manifest.json
    pronunciation-manifest.json  # 官方卡片发音音频
    release.json            # subjects / counts_by_subject
    exclusions.json
  active  -> content-20261030-01
  current -> content-20261030-01   # 兼容别名
  .archive/
    content-20261020-01/
```

### 4.2 多科目目标结构

所有 enabled 科目合并成一个 Release；Release ID 不再包含 subject：

```text
data/releases/
  content-20261030-01/
    exam.db                 # psychology + statistics
    knowledge.db
    assets/
      psychology/...
      psychology/audio/terms/   # 官方概念发音 mp3
      statistics/...
    assets-manifest.json
    pronunciation-manifest.json
    release.json
    exclusions.json
    release-diff.json       # 可选
  active -> content-20261030-01
  .archive/
    content-20261020-01/
```

说明：

- Release 目录名 = 全局唯一 `release_id`（`content-YYYYMMDD-NNN`）
- `active` 是唯一的全局指针；所有 enabled 科目同时切换
- `current` 是兼容别名
- 归档目录仍使用完整 Release ID
- 不再保留按 subject 独立的 active Release；P1.0 的 `active/<subject>` 仅作为过渡兼容读取

### 4.3 Release ID

格式：

```text
content-<YYYYMMDD>-<NNN>
```

示例：

```text
content-20261030-01
content-20261031-01
```

要求：

- 全局唯一
- 不包含 `/`、`..`
- 构建工具生成，不允许用户手填任意路径
- 发布后不可重命名
- `release.json` 中的 `release_id` 必须与目录名一致

### 4.4 迁移旧 Release

现有：

```text
data/releases/content-20261028-01/
data/releases/current -> content-20261028-01
```

迁移为合并 Release 的全局指针：

```text
data/releases/content-20261030-01/
data/releases/active  -> content-20261030-01
data/releases/current -> content-20261030-01   # 兼容别名
```

原 Release 目录不需要移动。  
API 优先读取 `active`，并校验 manifest 的 `subjects` / `subject_id` 包含请求科目，再回退到旧 `current`。  
P1.0 的 `active/<subject_id>` 布局仅作为过渡兼容；激活新 Release 时，如果该目录的子项全部是符号链接，会自动迁移为全局 `active` 符号链接。

## 5. Release 包规范

### 5.1 包内容

```text
<release_id>.tar.gz
  release.json
  exam.db
  knowledge.db
  assets-manifest.json
  pronunciation-manifest.json
  exclusions.json
  assets/
    psychology/...
```

可选：

```text
release-diff.json
build-report.json
```

### 5.2 release.json

```json
{
  "release_id": "content-20261030-01",
  "subjects": ["psychology", "statistics"],
  "schema_version": 1,
  "created_at": "2026-10-30T12:00:00+08:00",
  "source": "merged-subject-sources",
  "build_tool_version": "content-release-v1",
  "counts": {
    "papers": 75,
    "questions": 3489,
    "mcqs": 3465,
    "frqs": 24,
    "concepts": 1105,
    "kps": 1538,
    "practice_topics": 45,
    "exam_configs": 11
  },
  "counts_by_subject": {
    "psychology": {"questions": 2876, "concepts": 1105},
    "statistics": {"questions": 613, "concepts": 0}
  },
  "checksums": {
    "exam.db": "sha256:...",
    "knowledge.db": "sha256:...",
    "assets-manifest.json": "sha256:..."
  }
}
```

### 5.3 assets-manifest.json

```json
{
  "assets/psychology/images/2025/fig_q001.png": {
    "sha256": "...",
    "size": 123456,
    "mime": "image/png",
    "width": 1200,
    "height": 800
  }
}
```

要求：

- manifest 覆盖 Release 中被引用的所有 assets
- 文件实际存在
- 每个文件 checksum 与 manifest 一致
- 不引用 Release 外的本地路径

### 5.4 pronunciation-manifest.json

官方记忆卡片的发音音频单独记录，不混入图片 assets manifest：

```json
{
  "assets/psychology/audio/terms/mean-a22f090eed2e.mp3": {
    "path": "assets/psychology/audio/terms/mean-a22f090eed2e.mp3",
    "sha256": "...",
    "size": 7104,
    "mime": "audio/mpeg",
    "cluster_id": "psy-concept-...",
    "term": "Mean",
    "ipa": "min",
    "duration_ms": 832,
    "sample_rate": 24000,
    "bitrate_kbps": 64,
    "voice": "af_heart",
    "speed": 0.9,
    "engine": "kokoro-onnx"
  }
}
```

生成工具：`_tools/build_flashcard_pronunciations.py`。音标以 CMUdict（`eng-to-ipa`）为主，专业词回退到 `phonemizer + espeak-ng`；音频使用 Kokoro `af_heart`、0.9 倍速、64 kbps 单声道 MP3。

## 6. 本地构建流程

### 6.1 数据生产

```text
PDF / 教材
→ 解析
→ staging
→ QA
→ data/content/<subject>/<subject>_exam.db / <subject>_knowledge.db
→ 题目—概念关联
→ AI 解析（只写 options.ai_explanation）
→ 内容复核
```

### 6.2 构建 Release

```bash
python3 _tools/build_merged_release.py \
  --release-id content-20261030-01
```

构建会：

1. 复制内容源到 staging
2. 生成派生表
3. 复制 assets
4. 生成 `assets-manifest.json`
5. 生成 `release.json`
6. 运行 `validate_content_release.py`
7. 校验失败则不生成正式 Release

### 6.3 构建 Release Diff

构建时或发布前生成：

```text
release-diff.json
```

比较：

- 当前 active Release
- 候选 Release

Diff 至少包含：

```json
{
  "base_release_id": "content-20261028-01",
  "target_release_id": "content-20261030-01",
  "summary": {
    "papers_added": 0,
    "papers_removed": 0,
    "questions_added": 5,
    "questions_removed": 2,
    "questions_changed": 14,
    "concepts_added": 3,
    "concepts_removed": 1,
    "kps_added": 8,
    "kps_removed": 2,
    "links_added": 40,
    "links_removed": 7,
    "assets_added": 2,
    "assets_removed": 0
  },
  "items": []
}
```

Diff 只用于报告和审核，不用于服务器增量写入。

### 6.4 打包

```bash
tar -czf content-20261030-01.tar.gz \
  -C data/releases/content-20261030-01 .
```

实际构建工具应自动生成包和 checksum。

## 7. Release 上传与导入

### 7.1 可选上传方式

**推荐：CLI/rsync**

```bash
rsync -az --partial \
  content-20261030-01.tar.gz \
  server:/srv/ap-psych/incoming/
```

**Admin 上传**

```text
Admin → 发布 → 上传 Release 包
```

大文件上传建议：

- 分片上传到对象存储
- 或 Nginx `client_max_body_size` 调整到 200MB+
- 上传完成后由服务端校验

### 7.2 导入前的服务端校验

必须校验：

- 包格式合法
- 路径安全：拒绝 `../`、绝对路径、符号链接逃逸
- `release.json` 存在且可解析
- `subject_id` 合法
- `release_id` 与包名一致
- `exam.db` / `knowledge.db` checksum
- `assets-manifest.json` checksum
- SQLite `integrity_check`
- SQLite `foreign_key_check`
- counts 与 `release.json` 一致
- assets 文件存在且 checksum 一致
- 试卷配置、题目选项、FRQ rubric 等业务校验
- 不允许覆盖已存在的 Release ID

### 7.3 导入流程

```text
上传到 .incoming/<upload_id>/
→ 解包到 .staging/<release_id>/
→ 校验
→ 移动到 releases/<subject>/<release_id>/
→ 写入 content_releases 注册表
→ 等待人工激活
```

失败时：

- 删除 staging
- 不影响当前 active Release
- 返回具体错误
- 记录导入任务

### 7.4 管理接口

```text
POST   /api/v1/admin/releases/import
POST   /api/v1/admin/releases/{release_id}/activate
POST   /api/v1/admin/releases/{release_id}/archive
POST   /api/v1/admin/releases/{release_id}/restore
GET    /api/v1/admin/releases
GET    /api/v1/admin/releases/{release_id}/diff
```

内部 pipeline 可使用受限 service token：

```text
POST /internal/content/releases/import
Authorization: Bearer <pipeline-service-token>
```

不要把内部 service token 暴露给学生端或浏览器。

## 8. 激活与回滚

### 8.1 激活

合并 Release 激活 = 将全局 `current` 指向新 Release；所有 enabled 科目同时切换。

```text
data/releases/active -> content-20261030-01
```

原子步骤：

1. 确认 Release 存在且校验通过
2. 读取 manifest 的 `subjects` 列表
3. 创建临时符号链接
4. `os.replace` 原子替换全局 `active`（并同步 `current` 兼容别名）
5. 按 `subjects` 更新 `content_releases` / `content_active_release`
6. 为每个科目重建 `ContentStore` 并清缓存
7. 写审计日志
8. smoke test（`/content/version` + 各科目题目计数）

### 8.2 API 重新加载

API 不能永久缓存旧 Release。

每次 `get_store`：

```text
读取 active release 指针
→ 与当前 Store 对比
→ 如果 release_id/路径变化
→ 创建新 ContentStore
→ 清缓存
```

多 worker 下每个 worker 在下一次请求检测变化。

### 8.3 回滚

回滚不需要重新构建：

```text
将 current 切回旧 release
```

前置条件：

- 旧 Release 仍然存在
- 旧 Release 未归档
- 校验记录仍存在

回滚本身也要写审计日志。

### 8.4 归档

归档不是删除：

```text
data/releases/.archive/<release_id>/
```

规则：

- active Release 不允许归档
- 归档后可恢复
- 恢复后不会自动激活
- 归档不修改 Release 内容

### 8.5 是否删除

不要在 Admin 中提供普通删除按钮。

如果需要清理磁盘：

```text
CLI + 保留策略 + dry-run
```

建议保留：

- 当前 active
- 最近 5–10 个 Release
- 每月一个长期快照

删除前必须确认：

- 不是 active
- 不是回滚保护版本
- 没有正在进行的发布任务引用它
- 记录审计日志

## 9. Release Diff 与升级

### 9.1 全量快照

升级不是执行增量 SQL，而是生成新完整 Release。

```text
旧 Release：questions = 2876
新 Release：questions = 2881
```

服务器只切换 Release。

### 9.2 Diff 分类

- Question added
- Question removed
- Question changed
- Option changed
- Correct answer changed
- Explanation changed
- Rubric changed
- Asset added/removed/changed
- Concept added/removed/changed
- KP added/removed/changed
- Question-concept link added/removed
- Practice topic mapping changed
- Exam config changed

### 9.3 Diff 审核

激活前建议显示：

```text
题目新增 5
题目移除 2
题目修改 14
答案变化 3
解析变化 9
知识点新增 8
知识点移除 2
概念合并 1
图片变化 2
```

如果包含删除、答案变化、概念合并：

- 要求 super_admin 确认
- 保留 Diff 报告

## 10. 内容升级与 ID 规则

### 10.1 ID 是身份，不是题号

`psychology-cb26-u2-0001` 现在是“来源 + unit + 序号”型 ID。

发布后 ID 不应因为内容修正而重新生成。

### 10.2 升级匹配顺序

```text
1. 外部稳定 ID（如果来源提供）
2. paper_id + section + number + source_file
3. question_fingerprint（标准化题干/选项/答案/图片）
4. 模糊匹配 + 人工审核
```

### 10.3 场景规则

| 场景 | ID 处理 |
|---|---|
| 同一道题，修正题干/选项/解析 | 保持 ID，更新内容 |
| 同一位置被换成另一道题 | 旧 ID retired，新题新 ID |
| 题目移动序号，但内容不变 | 保持 ID，更新排序/显示号 |
| 新题加入题库 | 新 ID |
| 题目删除 | retired，不重用 ID |
| 不同来源但内容重复 | 保留两个 ID，建立 duplicate 关系 |
| 同 ID 内容完全不同 | 冲突，必须人工处理 |
| 教材新版 | 新 `book_id`，旧版保留 |

### 10.4 重复检测

重复检测不能直接合并 ID。

建议字段/表：

```text
questions.question_fingerprint
question_duplicates(
  question_id,
  duplicate_of,
  similarity,
  status,           -- candidate / confirmed / rejected
  reviewed_by,
  reviewed_at
)
```

规则：

- 同一来源同一题：匹配到旧 ID
- 不同来源内容相同：保留 ID，标记 duplicate
- 是否在练习中只展示 canonical 题，是产品决策
- 历史错题、attempt、笔记继续引用原 ID

### 10.5 CB 题库升级示例

```text
旧：psychology-cb26-u2-0001 = 题 A
新：同一题 A，但题干/解析修正
→ ID 不变
→ 新 Release 使用新内容
```

```text
旧：psychology-cb26-u2-0001 = 题 A
新：该位置变成题 B
→ 题 A retired
→ 题 B 新 ID
```

```text
新题库第 10 题与旧题库第 3 题内容重复
→ 两个 ID 都保留
→ question_duplicates 标记
```

## 20. Phase 2 具体实施方案

> 只有在 Phase 1 发布链路稳定后才进入。  
> Phase 2 的核心不是 AI，而是“服务器成为唯一可写内容工作区”。

### 20.1 前置条件

- Phase 1 Release 导入/激活/回滚已稳定
- 多科目 active 指针已完成
- Release Diff 已完成
- 历史 attempt 按 content_release_id 复盘已完成
- 服务器备份、审计、权限已具备

### 20.2 目标架构

```text
本地 Claude Code / prompts
  PDF / 教材
        │
        │ staging 包
        ▼
服务器 content workspace（唯一可写内容源）
        │
        ├── Admin 编辑
        ├── 解析 worker
        ├── AI worker
        └── 审核队列
        │
        ▼
服务器构建 Release
        │
        ▼

```

存储边界保持不变：

```text
内容工作区 / Release = SQLite
用户数据 = PostgreSQL
```

Phase 2 开始时，内容工作区先用 SQLite 单写者模式：

```text
/srv/ap-psych/content/workspace/psychology/
  exam.db
  knowledge.db
  assets/
```

要求：

- 单写者
- WAL
- 全局内容写锁
- AI/解析任务串行应用
- 不允许多个 worker 同时写 workspace

如果未来多人同时编辑或高并发，再迁 PostgreSQL content schema。

### 20.3 切到 Phase 2 的步骤

#### 切之前

1. 停止本地内容修改
2. 构建最后一个 Phase 1 Release
3. 备份本地科目源库 `data/content/<subject>/`
4. 备份 PostgreSQL
5. 记录 counts / checksums
6. 准备服务器 workspace 目录和读写权限

#### 切的时候

1. 上传本地内容源 DB 到服务器

```text
/srv/ap-psych/content/workspace/psychology/exam.db
/srv/ap-psych/content/workspace/psychology/knowledge.db
```

2. 校验：

```text
integrity_check
foreign_key_check
counts
assets
```

3. 用 workspace 构建一个 Release
4. 在 staging 验收
5. 正式启用 Admin 内容编辑
6. 本地改为 staging 生产者

#### 切之后

- 服务器 workspace 是唯一可写内容源
- 本地不再直接改生产 DB
- 本地只上传 staging 包
- 不允许本地整库覆盖 workspace

### 20.4 Phase 2 任务拆分

#### P2.0 服务器内容工作区

- 复制本地 DB 到 workspace
- `ContentWorkspace` 服务
- 写锁

- papers
- questions / options / rubrics
- KPs / concepts / links
- assets
- change type

#### P2.3 PDF 上传与 OCR

- 页面渲染

### 20.5 Phase 2 风险

- 本地/服务器双写
- 本地整库覆盖服务器修改
- AI 解析幻觉
- 扫描件 OCR 质量
- 图片/表格/跨页题

- worker 写入并发
- 版权材料访问控制
- AI 成本失控

对应措施：

- 单一可写源
- staging + 人工审核
- 处理前后备份
- 写锁/单写者
- 任务限额和成本监控
- 内容修订审计

### 20.6 Phase 2 不应做的事

- 不要直接让 AI 写正式 workspace
- 不要上传 PDF 后自动激活
- 不要让本地和服务器同时编辑

上线稳定后，再决定是否进入 Phase 2：

```text
服务器 workspace
→ 服务器构建
→ staging 导入
→ PDF/OCR
→ 教材/KP
→ AI worker
```

在 Phase 1 没有跑通之前，不建议先做服务器端 PDF 解析。
